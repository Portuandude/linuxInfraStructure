# 2026-09-13: CPU 자원 고갈 + 부하 인가 장애 주입 테스트 (계획된 테스트)

## 개요

`scripts/failover-test/03-cpu-exhaustion.sh app3`로 `app3` 인스턴스의 CPU를
`docker update --cpus=0.1`(0.1코어)로 강제 제한한 뒤, 그 상태에서 `peak.js`
(300 VU, 6분) 부하를 가해 전체 서비스에 미치는 영향을 관찰했다.

## 탐지

계획된 테스트 — k6 결과와 전/후 응답 시간 비교로 관찰.

## 영향 범위

**사용자 체감 실패 없음.** 300 VU 부하 중 39,178건 요청 전부 성공(0% 실패).
다만 최대 응답 시간이 평소 대비 크게 증가해, 일부 요청은 지연을 겪었을 것으로
추정.

## 원인 분석 (= 검증 대상 설계)

- `app3`만 0.1코어로 제한된 상태에서 Nginx `least_conn`이 여전히 1/3가량의
  트래픽을 `app3`로 보냄 — [네트워크 지연 테스트](2026-09-13-network-latency-test.md)와
  마찬가지로, "정상 응답이지만 느려진" 인스턴스는 자동으로 배제되지 않는다.
- 다만 이번엔 체감 영향이 훨씬 적었다: Express 자체는 매 요청마다 필요한 CPU가
  매우 작아(JSON 직렬화 수준), 0.1코어로도 대부분의 요청을 큰 지연 없이 처리할
  수 있었던 것으로 보인다. 즉 **CPU 제한과 네트워크 지연은 같은 "인스턴스 저하"
  상황이라도 사용자에게 미치는 영향의 크기가 다르다.**

## 결과

| 지표 | 정상 300 VU 테스트 (2026-09-13, rate limit 수정 후) | app3 CPU 0.1코어 제한 + 300 VU |
|---|---|---|
| 성공률 | 100.00% | **100.00%** (동일) |
| `http_req_duration` p95 | 840.69µs | **905.97µs** (거의 동일) |
| `http_req_duration` max | 5.71ms | **138.66ms** (약 24배 증가) |
| 처리량 | 108.17 req/s | 108.66 req/s (동일) |

- p95/평균/처리량은 거의 변화가 없어, **집계 지표만 보면 문제를 놓치기 쉽다.**
- 반면 **max(꼬리 지연)는 뚜렷하게 나빠졌다** — 실제 운영에서는 p99/max와
  Grafana의 인스턴스별 패널을 함께 봐야 이런 국소적 저하를 놓치지 않는다.

## 대응 조치

테스트이므로 `docker update --cpus=0`으로 제한 해제, 즉시 정상 응답시간(≈0.5~0.9ms)
으로 회복 확인.

## 재발 방지책

- 이번 테스트로 "평균/p95만으로는 단일 인스턴스 저하를 못 알아챌 수 있다"는
  점을 확인 — Grafana 대시보드의 "HTTP 요청률 (인스턴스별)" 패널처럼 **인스턴스
  단위로 쪼갠 지표**를 모니터링에 반드시 포함해야 하는 이유가 실증됨.
- [네트워크 지연 테스트](2026-09-13-network-latency-test.md)에서 확인한 것과
  동일한 한계(느린-정상 인스턴스 미배제)가 이번에도 재확인됨 — 재발 방지책도
  동일: 응답 시간 기반 능동적 배제(active health check/circuit breaker) 도입을
  향후 개선 과제로 남김.
