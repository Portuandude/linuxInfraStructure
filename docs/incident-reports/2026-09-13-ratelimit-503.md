# 2026-09-13: 300 VU 부하 테스트 중 82% 요청이 503으로 차단됨

## 개요

`scripts/loadtest/peak.js`(300 VU 피크 시나리오)를 실행했을 때, 전체 39,156건 요청 중
82.29%(32,223건)가 실패했다. `baseline.js`(20 VU)는 100% 성공했던 것과 대조적이었다.

## 탐지

k6 실행 결과에서 `http_req_failed` threshold(`rate<0.02`)가 즉시 위반되어 종료
(`ERRO thresholds on metrics 'http_req_failed' have been crossed`). 사용자가 실행 결과를
공유해 즉시 확인됨.

## 영향 범위

부하 테스트 환경 한정. 하지만 원인이 실제 운영 설정(Nginx `limit_req`)에 있었으므로,
실제 운영에서도 사내망(NAT) 뒤의 여러 직원이 몰릴 경우 동일하게 재현될 수 있는 문제였다.

## 원인 분석

1. `http_req_duration`이 매우 짧음(p95 1.02ms, max 6.14ms) — 실패가 "느려서"가 아니라
   "즉시 거부"되고 있다는 신호.
2. `infra/nginx/conf.d/app.conf`에 `limit_req zone=req_limit_per_ip burst=40 nodelay;`,
   `nginx.conf`에 `rate=20r/s`로 **IP당** 초당 20건(버스트 40건) 제한이 걸려 있었음.
   `nodelay`이므로 초과 시 대기 없이 즉시 503을 반환한다.
3. k6는 컨테이너 하나에서 300 VU를 실행하므로, Nginx 입장에서는 **모든 요청이 하나의
   출발지 IP**로 보인다. 300 VU가 평균 초당 100건 이상을 요청하면서 단일 IP 기준
   20r/s 한도를 크게 초과해 대부분이 차단됨.
4. 근본적으로, 이 rate limit 값은 "불특정 다수의 IP에서 오는 외부 트래픽 방어"를
   가정한 값이었다. 그런데 이 프로젝트는 **300인 규모 사내 서비스**로, 실제로도
   다수 직원이 같은 사내망 게이트웨이(NAT)를 통해 나가면 Nginx에는 소수의 IP로만
   보일 수 있다 — 즉 테스트 환경뿐 아니라 실운영 시나리오에서도 재현 가능한 설계 결함이었다.

## 대응 조치

- `nginx.conf`의 `limit_req_zone` rate를 `20r/s` → `1000r/s`로 상향
- `app.conf`의 `limit_req` burst를 `40` → `2000`으로 상향
- 변경 후 동일한 `peak.js`(300 VU) 재실행으로 검증 (결과는 아래 "검증" 참고)

## 재발 방지책

- 부하 테스트 시나리오에 300 VU(피크) 테스트를 필수 포함시켜, 이런 종류의 설정
  실수를 배포 전에 발견할 수 있도록 함 (이번 건도 그렇게 발견됨).
- Rate limit처럼 "IP당" 정책을 사용하는 설정은 실제 클라이언트 분포(사내망 NAT 여부)를
  먼저 확인하고 값을 정할 것 — 외부 공개 서비스와 사내 전용 서비스의 위협 모델이 다르다.
- 정말 개별 클라이언트 남용을 막고 싶다면, IP 대신 인증된 사용자 ID/세션 기준으로
  rate limit을 적용하는 방안을 추후 검토 (현재는 인증 체계가 없어 보류).
