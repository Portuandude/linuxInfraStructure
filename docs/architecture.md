# 아키텍처 설계

> 상태: 초안 (스캐폴딩 단계) — 구현 진행에 따라 갱신 예정

## 1. 요구사항

- 대상 규모: 사내 임직원 300명
- 가용성: 단일 인스턴스 장애 시에도 서비스 지속 (로드밸런싱 + 다중 App 인스턴스)
- 관측성: 트래픽/리소스/에러율을 실시간으로 모니터링
- 복원력: 장애 발생 시 자동/수동 복구 절차 존재

## 2. 컴포넌트

| 컴포넌트 | 역할 | 비고 |
|---|---|---|
| Nginx | 로드밸런서, 리버스 프록시 | upstream health check 포함 예정 |
| App (Node.js) | 사내 서비스 애플리케이션 | 다중 인스턴스로 수평 확장 |
| PostgreSQL | 주 데이터 저장소 | 볼륨으로 영속성 확보 |
| Prometheus | 메트릭 수집 | App/Nginx/시스템 메트릭 |
| Grafana | 시각화 대시보드 | Prometheus를 데이터소스로 사용 |
| node-exporter | 호스트 시스템 메트릭 노출 | CPU/RAM/디스크/네트워크 |
| cAdvisor | 컨테이너 단위 리소스 메트릭 | 컨테이너별 CPU/메모리 |

## 3. 트래픽 흐름 (예정)

1. 클라이언트 → Nginx(LB) : 443/80
2. Nginx → App 인스턴스 (round-robin / least-conn)
3. App → PostgreSQL (내부 네트워크만 허용)
4. Prometheus가 각 컴포넌트의 `/metrics` 엔드포인트를 주기적으로 스크랩
5. Grafana가 Prometheus 데이터를 대시보드로 시각화

## 4. 확장/장애 대응 포인트 (추후 상세화)

- App 인스턴스 스케일 아웃/인 (docker compose scale)
- DB 장애 시 대응 절차
- Nginx 헬스체크 실패 시 트래픽 우회
- 리소스 고갈(디스크/메모리) 시나리오

## 5. 다이어그램

상세 다이어그램은 구현 진행 후 실제 구성을 반영하여 추가 예정.
