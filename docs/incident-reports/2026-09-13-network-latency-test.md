# 2026-09-13: 네트워크 지연/패킷 손실 장애 주입 테스트 (계획된 테스트)

## 개요

`scripts/failover-test/02-network-latency.sh app1`로 `app1` 인스턴스의 frontend
네트워크 인터페이스에 `tc netem`으로 지연 500ms + 패킷 손실 10%를 주입하여,
(1) 단일 인스턴스 직접 호출 시 영향, (2) Nginx를 통한 분산 트래픽에서의 영향을
비교 관찰했다.

## 탐지

계획된 테스트. 단, **스크립트 자체를 두 차례 수정해야 실제로 재현에 성공**했다
(아래 "시행착오" 참고) — 이 과정 자체가 이번 테스트의 중요한 산출물이다.

## 시행착오

1. **1차 시도**: Nginx(`http://localhost/`)로만 요청을 보내 측정 → 응답 시간이
   전혀 변하지 않음. `least_conn`으로 3개 인스턴스에 분산되다 보니 효과가
   희석된 데다, 규칙이 실제로 걸렸는지 검증하는 단계도 없었음.
2. **2차 시도**: `app1` 컨테이너에 직접 접속하도록 스크립트를 바꿨지만 여전히
   효과 없음. 원인 조사 결과 **`app1`은 frontend/backend/monitoring 3개
   네트워크에 동시에 연결되어 있고, `eth0`가 frontend가 아니라 monitoring
   (172.20.2.0/24)이었다** (`eth1`=backend, `eth2`=frontend). `docker-compose.yml`의
   `networks:` 목록 순서(`frontend, backend, monitoring`)와 실제 인터페이스
   할당 순서(`eth0`=monitoring, `eth1`=backend, `eth2`=frontend)가 무관하다는
   것을 이번에 처음 확인했다.
3. **3차 시도**: `eth0` 하드코딩을 없애고, frontend 서브넷(`172.20.0.0/24`) IP를
   가진 인터페이스를 매번 동적으로 찾아 규칙을 걸도록 수정 → 성공.

## 원인 분석 (= 검증 대상 설계)

- `tc qdisc add dev <iface> root netem delay 500ms loss 10%`는 해당 인터페이스의
  **egress(나가는 트래픽)**에 적용된다. App이 보내는 응답이 지연/유실되므로
  클라이언트가 체감하는 RTT가 늘어난다.
- Nginx의 `app_backend` upstream은 `max_fails`/`proxy_next_upstream`이 **에러/타임아웃**
  기준으로만 동작하고, "정상 응답이지만 느림"은 감지하지 않는다 (passive health
  check의 태생적 한계). 따라서 느려진 인스턴스도 계속 `least_conn` 분배에 포함된다.

## 결과

| 구간 | app1 직접 호출 (Nginx 안 거침) | Nginx 경유 (3개 인스턴스 분산) |
|---|---|---|
| 사전 | 평균 0.7~0.8ms | 대부분 0.3~0.9ms |
| 장애 중 | **1.5s~2.8s** (평균 약 1.7s, 손실 발생 시 최대 2.8s) | 약 1/3은 0.5~1.0s로 지연, 나머지 2/3은 정상(1ms 미만) |
| 사후 (규칙 제거) | 0.7~0.8ms로 즉시 회복 | — |

- 단일 인스턴스만 보면 체감 지연이 **2,000배 이상** 증가하는 심각한 저하였다.
- 하지만 Nginx가 3개 인스턴스로 분산하고 있었기 때문에, 전체 사용자 트래픽
  기준으로는 **약 2/3이 영향을 받지 않았다** — 로드밸런싱이 단일 인스턴스
  장애의 영향 범위를 줄여주는 효과를 수치로 확인.
- 반면 나머지 1/3 사용자는 계속 느린 응답을 받았을 것 — **"느리지만 살아있는"
  인스턴스는 자동으로 배제되지 않는다**는 현재 설계의 한계도 함께 드러났다.

## 대응 조치

테스트이므로 규칙 제거로 즉시 정상화. 실제 운영 중 이런 상황이 발생한다면:
- Nginx의 `proxy_read_timeout`(현재 10s)을 넘기지 않는 "느린 응답"은 여전히
  해당 인스턴스로 계속 라우팅되므로, 사람이 개입해 해당 인스턴스를
  `docker compose stop`하거나 `weight`를 낮춰야 한다.

## 재발 방지책

- **응답 시간 기반 능동적 배제는 현재 미지원** — 향후 Nginx Plus의 active
  health check, 또는 App 자체에 circuit breaker를 두는 방안을 검토할 것.
- 장애 주입 스크립트에서 "네트워크 인터페이스를 이름으로 하드코딩하지 않는다"는
  교훈을 얻음 — 다중 네트워크에 연결된 컨테이너를 다룰 때는 항상 서브넷 IP
  기준으로 대상을 동적으로 찾을 것 (`scripts/failover-test/02-network-latency.sh`에
  반영 완료).
